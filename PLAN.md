## Phase 12 — Multi-agent voice platform (architecture decision 2026-09-29)
**Goal (user):** a flexible platform for building many voice agents, not one hospital agent. Every agent has its own
prompts, flow, skills, MCP / API tools, LLM, STT, TTS and settings, all stored in the database and edited from the
console. Providers (STT / LLM / TTS / embeddings) are DB records that can be added and updated without a deploy.
When a call starts, the agent is loaded **complete and frozen** for that call: flow, prompts, skills, tools, models,
voices, knobs. Reference: the Hamsa flow builder (reviewed 2026-09-29) — same structure, without its weak spots.

**Model (what the console manages):**
- **Workspace** — `workspace_id` on every table (one workspace, HMG, for now)
- **Secrets** — encrypted in the DB (key from `MASTER_KEY` in `.env`); referenced by name, never shown again
- **Providers** — named connections per kind (e.g. "Groq prod", "OpenAI-compatible KSA"): type, settings, secret refs, Test button. Edits apply to new calls
- **Tool library** — MCP servers (URL, transport, auth secret → tools discovered and cached) and API-request tools (URL, method, headers, typed params, timeout, Test). Per-tool policy: kind read / write / send, confirmation, timeout, cache, summarizer, result → variables
- **Skills / components** — reusable sub-flows (e.g. "Verify caller by mobile + OTP", "Pick a slot"), versioned, used by several agents
- **Agents** — name, languages, phone numbers / IVR extensions, draft + published release
- **Agent release** (immutable, versioned) — flow graph, global prompt + persona, global behaviours, phrases, variables, model routing (provider + model per purpose: agent, extraction, classification, transliteration), voice profile (STT hint, TTS voice per language, gates, barge-in, end silence), tools used, skill versions, knobs, post-call outcome prompts, webhook
- **Calls** record `agent_id` + `release_id`

**Flow graph (Hamsa's node set + fixes):**
- Nodes: Start · Conversation (static or prompted message, Jinja, AI-extracted typed variables with enums, per-node interruption, "global" nodes) · Tool (On success / On failure) · Router (conditions on variables) · Set variables · Sub-flow (skill) · Transfer call · Transfer to agent · Change settings · End call
- Transitions: variable conditions first; where the LLM must decide, a short classifier call picks from an enum — no paragraph-long edge texts
- **Global behaviours defined once per agent** (task switching, language lock, "a question is not a task", persona) instead of copied into every node — the Hamsa HMG agent copies them into ~10 nodes and needs ~150 nodes / 349 variable entries
- **Built into the runtime, not the prompt:** write / send tools only after a confirmation node (read-back + yes), no "booked / sent / cancelled" claim without a successful tool, grounding (only offer what a tool returned), attempt caps
- Voice layer unchanged (VAD, AEC, STT quality filter, confirmed barge-in, TTS normalization, phrase cache)
